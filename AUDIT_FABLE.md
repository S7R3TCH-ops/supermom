## Phase 2: Security — [x] done

**FLAG ONLY per fix policy — nothing in this phase was edited.** Ranked most→least severe.

### 🔴 CRITICAL — SEC-1: Public invoice route reads via browser anon client → RLS anon-policy scope is unverified and load-bearing
- `src/pages/InvoiceView.jsx:59` calls `fetchInvoiceById(id)` → `src/data/invoicesRepo.js:102` uses the **browser anon Supabase client** (`src/lib/supabase.js`, `VITE_SUPABASE_ANON_KEY`). Route `/i/:id` is mounted OUTSIDE the auth Gate (`src/App.jsx:490`).
- The query selects `invoices, clients(*), businesses(*), invoice_jobs(jobs(*))`. For an anonymous browser to read those tables, an **anon SELECT RLS policy must exist on all four**. Grepping every migration in `supabase/migrations/` finds ZERO `anon`/`TO public`/`TO anon` policies — every policy is `TO authenticated`. So the policy that makes this route work is applied **only in the Supabase dashboard, undocumented, unversioned.**
- **Failure scenario**: if that undocumented anon policy is broad (e.g. `FOR SELECT USING (true)` on `clients`/`jobs`/`businesses` to make the join resolve), then anyone holding the public anon key (shipped in the JS bundle) can enumerate **every client, job, and business across all tenants** — a full multi-tenant data breach. A scoped policy (e.g. only rows reachable from a known invoice id) would be safe, but there's no way to tell from the repo.
- **Suggested fix**: (a) Move the public invoice read behind `api/invoice.js` service-role with the id as the only input (endpoint already exists for PDF — add a JSON read handler), so no anon table access is needed; OR (b) capture the live anon policies into a committed migration and confirm each is scoped to invoice-reachable rows only. Until verified, treat as an open cross-tenant exposure. **This is the single highest-priority item in the whole audit.**

### 🔴 HIGH — SEC-2: AI endpoints have no auth and trust caller-supplied tenant IDs while using the service-role key
- `api/ai/chat.js:7` and `api/ai/[action].js` accept `businessId`/`clientId`/`jobId` straight from `req.body`, then query with the **service-role client** (`SUPABASE_SERVICE_ROLE_KEY`, bypasses RLS). No `Authorization` header check anywhere.
- **Failure scenario**: an unauthenticated attacker POSTs arbitrary IDs and reads any business's `owner_name`/`ai_profile`, any client's `notes`/`ai_context`, any job's notes — cross-tenant read — and burns Anthropic tokens on your key (cost/DoS). `chat.js` echoes the model reply, so it's a direct data-exfil channel.
- **Suggested fix**: require `Authorization: Bearer <supabase jwt>`, `supabaseAdmin.auth.getUser(token)`, then verify the token's user `business_id` matches the requested `businessId` (same pattern already correctly used in `api/admin/provision.js:28`). Reject mismatches with 403.

### 🟠 MEDIUM — SEC-3: `api/maps.js` is an unauthenticated proxy to billed Google APIs
- `api/maps.js` has no auth, no origin check, no rate limit. Distance Matrix is hard-capped 500 elements/day (CLAUDE.md). Anyone who finds the URL can exhaust the daily quota (wallet-DoS) and use your key as a free geocoding/distance proxy.
- **Suggested fix**: gate behind a Supabase JWT check like SEC-2, or at minimum verify `Origin`/`Referer` against the app domain. Also set a Google Cloud key restriction (HTTP referrer or per-key quota) as defense-in-depth — matches the "set Google Cloud quotas" memory note.

### 🟠 MEDIUM — SEC-4: `api/invoice.js` email handler is unauthenticated and side-effecting
- `handleEmail` (`api/invoice.js:124`) takes `invoiceId` + `clientEmail` from `req.body`, no auth. Anyone can trigger sending a real branded PDF to an arbitrary address and flip `jobs.invoice_sent_at`/`receipt_sent_at` on jobs they don't own (via `.in('id', jobIds)` at line 184, no business scoping). GET download is shareable-by-design (accepted), but the POST send path should not be open.
- **Suggested fix**: require the same Bearer-JWT ownership check as SEC-2 on the POST branch only; leave GET public.

### ✅ Soft-delete compliance: CORRECT (no findings)
- Normal delete flows use soft-delete: `softDeleteClient` (clientsRepo:111), `softDeleteJob`/`cancelJob`/`archiveClientJobs` (jobsRepo) all set `deleted_at`. Callers: EditClientSheet:134, ClientProfile:99 (archive), JobDetailSheet:190 all use soft variants.
- `hardDeleteClient`/`hardDeleteJob`/`revertJobToPreCompletion` are **explicit, separately-named "permanently delete" admin actions** behind their own confirm dialogs (ClientProfile:112 "hard delete", JobDetailSheet:202 "Job permanently deleted"). Intentional purge path, distinct from the default. Not a rule violation.
  - ⚠️ Minor note (not a defect): the hard-purge paths `.delete()` rows from `payments` (financial records) rather than voiding via the existing `payments.is_void` flag. If a purged job's payments were ever needed for tax/audit reconciliation they're gone. Consider voiding-not-deleting payments even on hard-delete. Low priority, admin-only, gated by confirm.

### 🟡 LOW — DATA-1: Some child-table writes filter by `job_id`/`invoice_id` only, not `business_id` (deviates from CLAUDE.md "every query" rule; RLS is the real guard)
- `jobsRepo.js:378-379` (`payments`/`invoice_jobs` delete by `job_id` only), `clientsRepo.js:123-124` (same), `jobsRepo.js:397-398,401,404` (invoice_jobs/invoices in revert loop). These omit `.eq('business_id', ...)`.
- **Why it's LOW not HIGH**: each runs after a business-scoped parent fetch (the job/client was already confirmed to belong to `businessId`), and RLS on those tables (per migration) blocks cross-tenant rows server-side regardless. So no actual cross-tenant write is possible today. It's a defense-in-depth / convention-consistency gap, not an exploit.
- **Suggested fix**: add `.eq('business_id', businessId)` to those child-table `.delete()`/`.update()` calls for belt-and-suspenders consistency with the documented rule. Purely additive, safe — but it's a data-layer change so FLAG ONLY per policy.
