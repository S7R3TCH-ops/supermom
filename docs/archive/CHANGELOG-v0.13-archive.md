## v0.13.39 (Aug 6, 2026) — LIVE (`77b79ee`)

**v0.13.39 (Aug 6) — sheet dead-space fix + Invoice/Receipt badge moved to header + Mark Paid/Edit Job row merge. Pushed live untested on a real notched device** (UI/CSS-only change, no schema/migration — cleanly revertible via `git revert 77b79ee` + push if the notch-clearance nudge looks wrong on Sandra's iPhone). Watch for: sheet header/grab-pill sitting under the notch or Dynamic Island. Joel flagged 3 small visual annoyances live-using the app: (1) completed-but-unpaid/partial job's footer had `Mark Paid` and `Edit Job` stacked as separate full-width rows when they could share one line; (2) the "Invoice Ready"/"Receipt Ready" card ate its own full-width footer row when it could be a small badge up front; (3) most sheets show a large dead-space gap between the last scrollable content item and the pinned footer.
1. **Root cause of (3), confirmed by reading the code, not guessed**: `PostJobSheet.jsx` and `NewJobSheet.jsx` used a fixed `height: calc(var(--app-height)*0.92)` on the sheet root, unlike every other sheet in the app (`JobDetailSheet`, `NewClientSheet`, `EditClientSheet`, etc.), which all use `maxHeight` (hug-content, capped) instead. A fixed height forces the inner `flex:1` scroll region to stretch to fill the leftover space even when a given step's content is short — that stretched empty flex space, rendered in the app's dark background color, is the "black blank space" Joel described. Fixed both to `maxHeight`, matching the pattern already proven correct in the other 10 sheets.
2. **Invoice/Receipt badge relocated** (`JobDetailSheet.jsx`) — was a full-width card in the footer (`{isPaid ? 'Receipt Ready' : 'Invoice Ready'}` + a VIEW button), now a small pink pill button next to the Status/Payment badges in the header (`Invoice · View` / `Receipt · View`), same `window.open('/i/:id')` behavior. Frees a full footer row.
3. **Mark Paid + Edit Job merged onto one row** for the specific completed-but-unpaid/partial state (`!isScheduled && !isPaid && !showWorkerPaid`, new `mergeMarkPaidEdit` flag) — previously each rendered as its own separate full-width `Btn`. Left every other state's footer layout (scheduled jobs, worker-owed jobs, the prepaid/invoiced edit-warning card) untouched — those already had good reasons for their existing row shapes. Caught and fixed one bug in review before shipping: the edit-policy warning card (prepaid/invoiced jobs) doesn't render the merged row, so the original suppression of `Mark Paid` in row 1 would have hidden it entirely while that warning card was open — fixed by scoping the suppression to `mergeMarkPaidEdit && !showEditWarn`.
4. **Top-margin nudge across all 10 sheets that cap sheet height** (`JobDetailSheet`/`WorkerCatalogSheet`/`NewClientSheet`/`EditClientSheet`/`PostJobSheet`/`NewJobSheet` 0.92→0.96; `ServiceCatalogSheet`/`NewExpenseSheet`/`FinanceDetailSheet` 0.88-0.90→0.92-0.94; `AiChatSheet`/`PrepNoteSheet` 0.85→0.89) — Joel asked whether sheets not stretching closer to full screen height was intentional; the gap is a deliberate bottom-sheet modality cue plus notch/status-bar clearance, but none of the 11 sheets had ever added explicit `safe-area-inset-top` padding of their own — the multiplier margin was the *only* thing keeping the sheet's rounded top corner clear of the notch/Dynamic Island. Before nudging any multiplier, added `paddingTop: env(safe-area-inset-top, 0px)` to the shared `GrabBar.jsx` component (used by all 11 sheets) as explicit, durable clearance, then nudged each sheet's cap up ~4 percentage points. This app has real prior history with exactly this failure class (the iOS white-bar saga, 4 shipped-and-failed fix attempts) — this specific change needs a real phone test on Sandra's iPhone (notched), watch for the sheet header/grab-pill sitting under the notch or Dynamic Island.
Build clean, Vitest 111/111. Pushed straight to `main` (LIVE) — Joel's explicit call, Sandra overseas (back ~2026-08-10) and needs the live build to test remotely.

## v0.13.37 (Aug 4, 2026)

**v0.13.37 (Aug 4) — `useFocusTrap` stale-closure and dead-keydown-listener fixes.** Found while scoping Statler Phase 2's `<Sheet>` primitive and ported back here since the bug is real and pre-existing. Two issues in `src/hooks/useFocusTrap.js`: (1) `onClose` was captured directly in the effect's closure — any inline `onClose` passed from a parent (a fresh function reference every render) restarted the whole effect, including the 350ms autofocus timer, on every parent re-render; now held in a `useRef` so the effect's own deps don't include it. (2) The `keydown` listener (Escape to close, Tab-wrap) was attached inside the same code path as the autofocus branch's early-return, so on any sheet that actually autofocused (nearly all of them) the listener silently never attached — Escape and Tab-wrap have been dead in practice. Listener now attaches unconditionally whenever the trap is active. No behavior change to the 11 sheets consuming this hook beyond fixing both bugs — same public API. Build clean, Vitest 111/111.

## v0.13.33 — Jul 23, 2026 (LIVE, pushed to main)

Sandra's business is live — data wiped and re-provisioned Jun 9. App in active use.

**v0.13.33 (Jul 23) — real fix for the Clients page "black bar" under the filter pills. LIVE (`a960505`).** Joel phone-tested v0.13.31's keyboard-squeeze fix (confirmed working) but found the Clients page still had a large dark-empty-space bar directly under the filter chip row — screenshot showed it with **5 real results on screen**, ruling out v0.13.31 item 2's fix (which only narrowed a `filtered.length<=2` centering trigger to `===0` — a real, separate fix, still correct, just not the cause of this). Root cause: the global `.sm-scroll::after` CSS rule (`index.css`) appends an invisible `height:100px` block after *every* element with class `sm-scroll`, so a vertical list's last card always clears the floating `+` nav button. `Clients.jsx`'s filter-chip row (`className="sm-scroll"`, a horizontal `overflowX:auto` scroller) only wanted that class for its scrollbar-hiding styles, not the FAB-clearance block — but got both, forcing the whole ~26px-tall pill row's flex container to reserve 100px, rendering as a big dead-space bar underneath. Fix: new `.hscroll` class (scrollbar-hiding only, no `::after`) for horizontal scrollers; swapped the filter row from `sm-scroll` to `hscroll`. `NudgeDraftSheet.jsx:71` has the identical latent pattern (horizontal scroller using `sm-scroll`) — not reported broken, left untouched, flagged for whoever touches it next. Build clean, Vitest 111/111.

**v0.13.32 (Jul 23) — Home screen stale-payment-amount fix. LIVE (`5a8584c`).** Investigated as part of the "Mark Paid on Completed+Partial" E2E-reported bug (see Bugs list — that one turned out to be a Playwright/CDP automation artifact, confirmed via Joel's manual desktop test, no code change needed there). While Joel tested that manually, he found a real, separate bug: after marking a job Completed+Partial via PostJobSheet, Home's job card status tag updated instantly but the dollar amount stayed stale until a manual page refresh. Root cause: `Home.jsx` maintained its own separate, manually-fetched `paymentMap` (`useEffect` + raw Supabase `payments` query), gated on the *set* of job IDs on screen rather than on the app's actual `notifyDataChanged`/`queryClient.invalidateQueries()` invalidation chokepoint — so a new payment on a job already in the list never re-triggered it, while the status tag (sourced from `useJobs()`'s properly-invalidated React Query cache) updated fine. Fix: deleted the entire redundant fetch — `useJobs()` already computes a correct, always-fresh `amount_paid` field on every job via `toDisplayJob()` (`src/data/selectors.ts:322`), the same path every other amount on Home already reads from. Net simplification (fewer lines, one fewer Supabase round-trip per render), not a patch. Build clean, Vitest 111/111.

**v0.13.31 (Jul 23) — 4 fixes from Joel's real on-device phone-test of v0.13.30. LIVE (`9b567e1`).**
1. **Home screen dead-space regression, cherry-picked from `claude/home-page-issue-zti5q0` (`aaf296b`, previously unmerged).** v0.13.30's dead-space fix centered Home's scroll container (`justifyContent:center`) whenever total item count was ≤2 — but 2 real "Needs attention" cards is normal daily content, not an empty state, so it produced a large blank gap instead of top-aligned content. Home has no "no results for filter" case like Clients does, so the centering behavior is dropped there entirely; reverts to normal top-aligned block flow.
2. **Clients page — same regression class, `Clients.jsx`.** Same `justifyContent:center` trigger was `filtered.length <= 2`, which fired for real short-but-nonzero result sets (e.g. filtering to 1-2 clients), not just the true empty state — visually read as a gap between filter chips and the first card. Condition narrowed to `filtered.length === 0` (the true empty state already has its own dedicated centered block just above) — short-but-nonzero results now top-align like the normal case.
3. **New Job "Recent clients" avatar initials invisible in dark mode** (Joel, screenshot evidence) — root cause confirmed: `NewJobSheet.jsx`'s "Recent clients" avatar circle (line ~547) never set an explicit `color` on the initial-letter text, so it fell all the way through to `body`'s CSS `color: var(--ink)` (`index.css`) — a **fixed light-mode value** (`#2D2D2D`, near-black) that's never overridden for dark mode, since this app's real dark/light theming runs entirely through JS `tokens.js` inline styles, not CSS custom properties. Every other text element in this sheet explicitly sets `color: T.ink`/`T.pink`; this one avatar spot didn't, so in dark mode it rendered near-black initials on a barely-tinted dark pink circle — invisible. Fixed: explicit `color: T.pink` added, matching the existing `T.pink`/`T.pinkTint` border/background already on that element. 4. **Sheet keyboard-squeeze: pinned footer action row eats disproportionate space when the keyboard is up.** Root cause confirmed: `appHeight.js` correctly re-pins `--app-height` to `visualViewport.height` on keyboard show (working as designed), and sheet `maxHeight` (`calc(var(--app-height)*0.92)`) correctly shrinks with it — but each sheet's own fixed-height chrome (header + pinned footer button row) doesn't shrink or hide, so on an already-small keyboard-reduced viewport that fixed overhead eats a much larger *fraction* of the total, squeezing the actual scrollable form content down to a sliver. Every affected sheet already computes `isKeyboardFocused` via the existing `useKeyboardFocus()` hook (previously only used to add a 260px bottom spacer). Fix: reuse that same flag to hide the pinned footer action row entirely while the keyboard is focused — it reappears the moment the field blurs. Applied to the 3 sheets with a genuine separate (non-inline) pinned footer: `JobDetailSheet.jsx` (EditMode's Cancel/Save row), `NewExpenseSheet.jsx` (Cancel/Log Expense row), `NewJobSheet.jsx` (Back/Next/Confirm step-nav row). `EditClientSheet.jsx`/`NewClientSheet.jsx` were checked too — their Save button is inline in the scrollable content (no separate pinned footer), so they weren't affected by this bug and weren't touched.
